# Agentic AI Use Case Builder (FDA-CLI method)

Scaffolds a complete, runnable Agentic AI demo for **any** vertical using the **Flogo Design CLI (`flogodesign-cli`, aka `fda`)** to construct every app command-by-command. You supply the domain; this skill supplies the structure, the exact `fda` command recipes, and the runtime gotchas that are easy to get wrong.

This is the sibling of the `agentic-ai-use-case` skill. **Same output, different build method:**

| | `agentic-ai-use-case` | **`agentic-ai-use-case-fda` (this skill)** |
|---|---|---|
| How apps are built | Clone an existing `.flogo` JSON and swap fields | **`fda` commands only — never edit app JSON directly** |
| Best when | You have a near-identical reference app to copy | You want a clean, auditable, from-scratch build with no leftover UUIDs/secrets/contrib blobs |
| Verification | Import + live run | **Build to `.exe` with `flogobuild` and (optionally) live-run against PostgreSQL + your LLM** |

> **Hard rule for this skill:** every structural change to a `.flogo` file goes through an `fda` subcommand (`cp`, `cap`, `cc`, `ct`, `cf`, `ca`, `cth`, `wth`, `cs`, `sa`, `mm`, …). The **only** direct-JSON touch permitted is passing a JSON *value* to `fda sa … --jsonValue`/`--jsonFile` (which is still an `fda` call). Do not open a generated `.flogo` in an editor and change nodes by hand.

> **Hard rule #2 — once a `.flogo` has been opened/edited in the designer, NEVER regenerate it to fix a bug.** Re-running the whole build driver (or any `fda cc`/`cap` that recreates connections/properties) **wipes every manual edit**: it reverts secret values (DB password, email password, API key) back to their placeholders **and** mints a *new* connection UUID, which orphans every activity `input.Connection` (`conn://<id>`) and every orchestrator `mcpServers`/`remoteAgents` ref → the designer clears them to `""` on next save (empty dropdowns, "Connection is required"). For a bug in a designer-touched file, make the **minimal, surgical** change to only the broken field(s) on the existing file (read the current connection id back from that same file and set the literal), leaving secrets and Synced schemas byte-for-byte intact. This is the one case where a targeted direct-JSON edit of a single value is preferable to re-running a generator. (Real failure: a driver re-run reverted the user's DB password twice and left all 6 A2A postgres activities with empty connection dropdowns.)

> **Hard rule #3 — do NOT build binaries unless the user explicitly asks.** Never run `flogobuild build-exe` proactively (e.g. "to verify a fix"). Design-time verification (`python -m json.tool`, `fda cm`, grep that refs resolve) is always fine and expected; producing an `.exe`/binary is opt-in only. When the user *does* ask for a build, run it in the foreground (real-time output), never in the background.

## What it produces

A new folder (default `demos/Agentic_AI/<UseCase>_Use_Case/`, confirm with the user; **never** inside `skills-library/`) containing:

| File | Purpose |
|------|---------|
| `database.sql` | PostgreSQL schema + demo data, engineered so each demo scenario works |
| `reset_data.sql` | TRUNCATE + reload; clears agent-written tables; volatile dates relative to today |
| `<Prefix>MCPServer.flogo` | **1 MCP Server** — N read-only tools, each querying one table/join |
| `<Prefix>A2AServers.flogo` | **1 A2A Agents app** — M action agents that **write directly to PostgreSQL** (`act_postgresql_query`/`act_postgresql_insert`) or send email, each its own trigger/port. **No separate REST/backend app unless the user explicitly asks** (see the default-action hard rule below). |
| `<Prefix>AIOrchestrator.flogo` | **1 AI Orchestrator** — WebSocket trigger + AI Agent activity routing to MCP tools / A2A agents |
| `prompts.md` | Demo prompts grouped by scenario |
| `README.md` | **Authored FIRST as the approval artifact** (use case, persona, planned apps/tools/agents, sample prompts, how-to-run), then **finalized at the end** with real ports/commands + the **"below things are not configured…"** section. Architecture, apps/tools/agents tables, DB summary, demo scenarios, prerequisites + setup, ports, troubleshooting. |

Architecture (shared by all reference use cases):

```
Chatbot UI --WebSocket--> AI Orchestrator --MCP(HTTP streamable)--> MCP Server --\
                                 |                                                +--> PostgreSQL
                                 \-----------A2A (HTTP)-----> A2A Agents ---------/   (+ SMTP for email)
```
- **MCP Server** = read-only lookups. Stateless, safe to retry; the LLM picks tools by their description.
- **A2A Agents** = action workflows — **write directly to PostgreSQL** (`act_postgresql_query` to validate, `act_postgresql_insert` for INSERT/UPDATE) or send email (`act_general_sendmail`). Own guardrails, separate deploy/scale.
- **Orchestrator** = the AI brain. WebSocket chat; the LLM decides intent and calls MCP tools or hands off to A2A agents.

> **Default-action hard rule (verified across the reference use cases):** A2A action agents write **directly to PostgreSQL** or send **email** — the canonical write flow is `noop → log → [query to validate] → insert → log → actreturn`, and every use case includes one dedicated `send_confirmation_email` agent (`noop → sendmail → log → actreturn`). **Do NOT create a separate REST/backend service app, and do NOT use `act_general_rest` in the A2A agents, unless the user explicitly asks for a REST backend.** Of the six reference use cases, five (Airline, Life & Pensions, Power Distribution, Retail Banking, Telecom) write directly to Postgres; only **Hospital** calls a REST backend, and it is the documented outlier — do not copy its `#rest` pattern for a default build.

## Two entry paths

**Default path — the user gives only a domain/industry/vertical (no spec, no README).** Run the interactive discovery below: **persona-first questions (Phase 1–2) → author the README as the approval artifact (Phase 3) → get explicit approval → build (Phase 4) → finalize + verify (Phase 5)**. This is the common case and the one the reference use cases were built from.

**Alternate path — the user provides a filled `*.spec.md` or an existing README.** Read it and treat it as Phase 1–2 input (the user owns the WHAT/WHY; this skill owns the HOW). Map it → build: information lookups → MCP tools, actions/workflows → A2A agents (direct-Postgres writes by default), entities → PostgreSQL tables, scenarios/seed-data → `database.sql` + `prompts.md`, acceptance criteria → the Phase 5 verification. You can skip the discovery questions the spec already answers, but still confirm the persona and the README before building.

Either way: the **user owns the spec/intent**, **this skill owns the plan + implementation**. The sibling `*.spec.md` template ([../agentic-ai-use-case/references/use-case-spec-template.md](../agentic-ai-use-case/references/use-case-spec-template.md)) is optional scaffolding — the README (Phase 3) is the artifact the user actually approves.

## Workflow — always follow these phases in order

### Phase 0 — Read environment config, print tool paths+versions
Read `skills-library/.claude/skills/config.md` first for: the `psql` path and PostgreSQL host/port/user/password/db; the OpenAI/LLM API key, base URL, and model; the SMTP username/app-password; and the CLI paths for `flogodesign-cli` (`fda`) and `flogobuild`. **Do not hardcode any of these** — read them at build time. Before running any command, print the resolved `fda` and `flogobuild` **path and `version`** so the run is reproducible. Read secrets from config.md into shell/script variables; never echo them.

### Phase 1 — Identify the persona FIRST (ask before anything else)
When the user gives only a domain, the **very first question is WHO the end user is** — because the persona determines the tables, the tone, and which actions exist. Ask an either/or framed to the domain, e.g.:
- Airline → *"Is this for the **passenger/customer** (self-service) or the **airline operator/agent** (back-office)?"*
- Banking → *"the **account holder** or a **branch/call-center agent**?"* · Utilities → *"the **resident/customer** or a **grid operator**?"* · Hospital → *"a **patient** or **hospital staff** (discharge coordinator)?"*

Most reference use cases are **customer-facing self-service** (5 of 6); Hospital is the one operator-facing example. Once the persona is fixed, state back in a few lines: (1) how that persona interacts (they chat over WebSocket; the orchestrator answers and can perform actions on confirmation); (2) what problem is automated (the business outcome); (3) the solution shape (1 MCP server of read tools, 1 A2A app of direct-Postgres action agents, 1 orchestrator, PostgreSQL-backed).

### Phase 2 — Discover operations (use AskUserQuestion), in this order
After the persona is set, ask what changes the build — **persona → operations → read-vs-action → multi-step**:
1. **What operations does this persona perform?** Propose a default list for the domain+persona and let the user confirm/trim.
2. **Which are read-only lookups vs state-changing actions?** Read-only → **MCP tools**; state-changing → **A2A agents**. Propose the split.
3. **Which actions are multi-step agentic workflows** the orchestrator must chain across several agents/tools in one prompt (e.g. "full discharge = book appointment + order meds + free the bed + email summary")? These drive the orchestrator's routing system prompt and the full-workflow demo prompts.
4. **Action type per A2A agent** — default is a **direct PostgreSQL write** (`insert`/`update`) or **email**. Only ask about a REST-backend agent if the user brings it up; otherwise assume direct-Postgres (do NOT create a REST app — see the default-action hard rule).
5. **Email/notification agent?** → include one dedicated `send_confirmation_email` SMTP agent (creds from config.md); the reference use cases all have exactly one.
6. **LLM provider** → provider + model + base URL (defaults from config.md; e.g. OpenAI `https://api.openai.com/v1`). The base URL must be an explicit endpoint (see gotcha 4c).
7. **Locale/persona details** → names, IDs, currency so demo data feels real (each reference use case has a flagship persona with a stable ID pattern, e.g. `MBR-100001`, `+1-415-555-0142`).
8. **Ports & folder** → default to a free port block and `demos/Agentic_AI/<UseCase>_Use_Case/`; confirm.

### Phase 3 — Author the README FIRST, then GATE on approval  ⛔
Write the **`README.md` before building any database or app** — it is the approval artifact (it replaces the old abstract plan doc). Draft it to the reference-use-case shape: title + intro, the **persona**, an architecture overview (ASCII diagram), the **planned apps** with their **tools table** (name → table/query) and **agents table** (name → action type + workflow), the **database tables** it will need, **sample prompts** (grouped MCP-only vs MCP+A2A, including the multi-step full-workflow prompt), and **how the user will run it**. Also list **what will land in the manual-config gap section** (see Phase 5 / the reference).

Then **STOP and get explicit user approval on the README before creating any database or apps.** (You may present it via `EnterPlanMode`/`ExitPlanMode`, or just ask the user to confirm the README.) Do not proceed to Phase 4 until the user approves. This is a hard gate — it is the single point where the user shapes the whole use case cheaply, before any `.flogo` exists.

### Phase 4 — Build with `fda` (only after README approval; later steps depend on earlier names)
1. `database.sql` — schema + **dummy/demo data** engineered per scenario (one clean case + one exception case per write-agent). Agent-written tables (disputes, tickets, orders, callbacks…) start empty. See the sibling `data-and-docs.md`.
2. `reset_data.sql` — same data, agent-written tables emptied, volatile dates relative to today.
3. `<Prefix>MCPServer.flogo` — build with `fda` per **[references/fda-build-recipes.md](references/fda-build-recipes.md) § MCP Server**. One read tool per lookup, each `act_postgresql_query` against a table/join; each tool handler MUST get input+output schemas (gotcha 1) or the MCP runtime panics.
4. `<Prefix>A2AServers.flogo` — build with `fda` per **§ A2A Agents**. One `tr_agent` trigger per agent; wire the tool handler with `--input toolParams:object --output response:object` + schemas. **Default action = write directly to PostgreSQL** (`act_postgresql_query` to validate → `act_postgresql_insert` for INSERT/UPDATE) or `act_general_sendmail` for the email agent. **Do NOT build a REST-backend agent (`act_general_rest`) or a separate backend app unless the user explicitly asked** — if they did, use the opt-in REST steps in the recipe.
5. `<Prefix>AIOrchestrator.flogo` — build with `fda` per **§ Orchestrator**. Create the LLM/MCP/A2A connections, read their `conn://` UUIDs back from the file, then set `mcpServers` / `remoteAgents` arrays with `sa activity --jsonValue`. Apply the **three wsserver gotchas** (headers output schema, `wsconnection`/`content` = `any`, real LLM base URL).
6. **Finalize the README** (from Phase 3) + `prompts.md`: fill in the real ports, exact start commands, and append the manual-config gap section — **ending by telling the user exactly what they must configure manually to run end to end** (see Phase 5 / [references/manual-config-gap.md](references/manual-config-gap.md)).

Scripting the `fda` calls (a small Python or bash driver that shells out to `fda`) is encouraged for repeatability — the recipes reference file shows the pattern. **On Windows/Git-Bash, prefix `fda` calls with `MSYS_NO_PATHCONV=1`** (or drive `fda.exe` from a Python `subprocess`) so `/`-selectors and URLs aren't path-mangled.

### Phase 5 — Verify (do this before declaring done)
- **Data:** create/refresh the DB, load `database.sql`, confirm row counts; confirm `reset_data.sql` reloads clean. Run the **exact** SQL from every MCP tool and every A2A query against the DB — this catches any table/column mismatch.
- **Static:** `python -m json.tool` each `.flogo` (must parse); `fda cm` (check-mappings) each app. **Verify refs RESOLVE, don't just eyeball their format** — for every `input.Connection` and every orchestrator `mcpServers`/`remoteAgents` entry, confirm the `conn://<uuid>` actually matches an `id` in that file's `connections` map (a `conn://` string pointing at a stale/wrong id is dangling and the designer silently clears it → empty dropdown). Also confirm the orchestrator's MCP/A2A `serverUrl`s match the MCP/A2A ports, and that no secret still holds its placeholder if the user intended to set it. (Counting that refs are non-empty `conn://` strings is NOT verification — a real failure slipped through exactly this way.)
- **Build (only if the user explicitly asks — Hard rule #3):** `flogobuild build-exe -f <app>.flogo -c <context>` for each app, in the foreground. Note the cosmetic exit-1 path bug (the `.exe` is still produced next to the `.flogo`; verify by timestamp/size). Do **not** build proactively to "verify a fix" — static checks above are the default verification.
- **Live run (if requested):** start MCP → A2A → Orchestrator, then send a WebSocket prompt and confirm the LLM calls an MCP tool that returns real DB rows and the answer is written back. See the recipes reference for the exact start/test sequence.
- Tell the user precisely **what was verified vs. what remains** — and hand them the manual-config gap checklist, which now includes the **FDA Tech-Preview manual steps** (Sync every trigger, validate every connection, set the email password as a `SECRET:` value, and any certificates/branches/loops/error-handlers the use case needs). See [references/fda-limitations.md](references/fda-limitations.md).

## Key facts (verified by a full FDA-only rebuild + live run of a reference use case)

Agentic type IDs used by `fda`:

| Component | Trigger ref | Activity refs | Connection refs |
|---|---|---|---|
| MCP Server | `tr_mcpserver` | `act_postgresql_query`, `act_default_actreturn` | `con_postgresql` |
| A2A Agents | `tr_agent` (one per agent) | `act_postgresql_query`, `act_postgresql_insert`, `act_general_sendmail`, `act_general_log`, `act_default_actreturn`, `act_default_noop` · *(opt-in only if user asks: `act_general_rest`)* | `con_llmprovider`, `con_postgresql` |
| Orchestrator | `tr_wsserver` | `act_agenticai_agentactivity`, `act_websocket_wswritedata` | `con_llmprovider`, `con_mcpserverconfig`, `con_a2aserverconnection` (one per A2A agent) |

- **MCP Server** — `tr_mcpserver` settings: `serverType HTTP`, `serverPort` (from a property), `serverEndpointPath /<usecase>mcpserver`, `serverName`/`serverVersion`. Each tool = a handler (`--mcpHandlerType Tool --mcpHandlerName <Name> --mcpHandlerDescription "<rich desc>"`) → a flow of `act_postgresql_query → act_default_actreturn`. Read pattern: `SELECT * FROM public.<table> ORDER BY <pk> ASC;` (the LLM filters). Tool descriptions must be rich — the LLM chooses tools from them.
- **A2A Agents** — one `tr_agent` per agent, each with its own `agentName`, `agentDescription`, `agentType "A2A Server"`, `agentPort`/`agentUrl` (properties), `model` (property), `temperature`/`memoryMaxSize` (number), `enableGuardrails`/`redactSensitiveData` (boolean), `conversationStoreType`, and a `systemPrompt`. Each has a Tool handler with `agentToolName` + `agentToolDescription`, wired with `--input toolParams:object --output response:object` and `toolParams`/`response` schemas. **Default action flow (direct Postgres):** `act_default_noop → act_general_log → act_postgresql_query (validate) → act_postgresql_insert (INSERT/UPDATE) → act_general_log → act_default_actreturn`. The email agent uses `act_default_noop → act_general_sendmail → act_general_log → act_default_actreturn`. *(Opt-in only, if the user explicitly asked for a REST backend: swap the DB write for `act_general_rest (×N)` — see gotcha 2b and the recipe's opt-in REST steps.)*
- **Orchestrator** — `tr_wsserver` (port from property; handler `path /<usecase>`, `mode Data`, `format String`) → flow `act_agenticai_agentactivity → act_websocket_wswritedata`. The agent activity lists the MCP connection under `mcpServers` and all A2A connections under `remoteAgents` (set via `sa activity --jsonValue '["conn://…"]'`), with a `systemPrompt` holding the routing rules. `input.userPrompt = =coerce.toString($flow.content)`; `wswritedata.input.message = =$activity[AIAgent].response`, `.wsconnection = =$flow.wsconnection`.
- **Connections per app:** MCP → 1 `con_postgresql`. A2A → 1 `con_llmprovider` + 1 `con_postgresql` (needed by default — action agents write to the DB). Orchestrator → 1 `con_llmprovider` + 1 `con_mcpserverconfig` (serverType `http`, `httpTransportType streamable`, `serverUrl` = MCP URL) + one `con_a2aserverconnection` per A2A agent (`serverUrl` = that agent's URL).
- **Ports & URLs:** give each app/agent a distinct port (all from app properties); the orchestrator's MCP/A2A `serverUrl`s must point at the MCP/A2A ports.
- **Secrets & endpoints:** LLM API key, PostgreSQL password, SMTP app-password come from `config.md` and are stored as app properties (mark true secrets as `SECRET:` where supported). The LLM **base URL must be an explicit endpoint** (see gotcha 4, third bullet).

## Top gotchas (each of these caused a distinct, real failure — the recipes bake in the fixes)

1. **MCP tool handlers need input AND output schemas or the MCP runtime panics** (`missing input schema`). For every tool: `fda cs <Args> '{"type":"object","properties":{}}'` and `fda cs <Resp> '{"type":"object","properties":{"data":{"type":"string"},"error":{"type":"string"}}}'`, then `fda sa handler "<Trig>.<flow>.schemas.output.arguments" <Args> -C schema --force` and `… .schemas.reply.response <Resp> -C schema --force`. (`tr_agent` handlers likewise need `toolParams`/`response` schemas.)
2. **`actreturn` object mapping needs the `.mapping` node:** map `<flow>.Return.input.mappings.response.mapping.data`, NOT `…response.data`.
2b. **(Opt-in — REST backends only)** **REST activity `responseBody` must be declared as an output schema, or downstream mappings break.** *Applies only when the user explicitly asked for a REST-backend agent; the default A2A agents write directly to Postgres and never hit this.* The `#rest` (`act_general_rest`) activity always exposes `statusCode`/`responseTimeInMillis`/`headers`, but **`responseBody` only exists if you set `schemas.output.responseBody`** — `ca`/`ct` don't create it. Without it, a Return/mapper that references `$activity[InvokeRESTService].responseBody` shows a red ✗ on "Map Outputs" (the field is unresolvable). Fix: `fda sa activity "<flow>.InvokeRESTService.schemas.output.responseBody" --jsonFile <file> --force` where the file is `{"type":"json","value":"<stringified draft-04 schema of the response fields>","fe_metadata":"<sample JSON>"}`. Do this for **every** REST activity whose body is consumed downstream. (Same idea for other activities that expose a schema-driven output.)
3. **`conn://` arrays ARE automatable — not a manual step.** After `fda cc`, read the connection UUIDs back from the `.flogo` file, then `fda sa activity "<flow>.AIAgent.settings.mcpServers" --jsonValue '["conn://<uuid>"]'` and `…remoteAgents --jsonValue '["conn://<a2a-uuid>",…]'`.
4. **wsserver orchestrator — three fixes (all required for a working WS reply):**
   - **Handler needs `schemas.output` present** or the wsserver trigger nil-panics on the first request. Attach the standard WS headers output schema: `fda cs <WsHeaders> '<headers schema>'` + `fda sa handler "<Trig>.<flow>.schemas.output.headers" <WsHeaders> -C schema --force`.
   - **`wth` converts type `any` → `object`** (only `params` survives). Typing `content`/`wsconnection` as `object` coerces the live WS connection into a plain map → `wswritedata: "Configured connection is not a WebSocket Connection"`. After `wth`, rewrite the whole array: `fda sa flow "<flow>.metadata.input" --jsonFile <file>` with `wsconnection` and `content` = `any`. (Per-element selectors like `…input.wsconnection.type` do **not** mutate arrays — they add phantom keys.)
   - **LLM base URL must be a real endpoint.** `fda cap` turns an empty value into the literal `New_value` → runtime posts to `/New_value/chat/completions`. Set e.g. `https://api.openai.com/v1`.
5. **App properties have no value-setter** — only `cap` (create) and `rap` (remove). To change a value, `rap` then `cap`; connection/activity refs to it survive (they key by name).
6. **PostgreSQL parameters** (for parameterized reads/writes) go via `input.mapping.parameters`, not `RuntimeQuery` — see the sibling `postgres-activity-patterns.md` for the semantics and the recipes file for the FDA way to set them.
7. **Windows/Git-Bash:** prefix `fda`/`flogobuild` with `MSYS_NO_PATHCONV=1` (or drive `fda.exe` via Python `subprocess`) so URLs and `/`-selectors aren't mangled. Run builds in the foreground (real-time output).
8. **A2A agent flows need the `toolParams` schema on the FLOW input — and `metadata.input` alone is NOT durable in the designer.** `wth --input toolParams:object` writes a **bare** `object` to `flow.metadata.input`, so the designer's Input tab can't resolve `$flow.toolParams.<field>` and shows a red ✗ on every toolParams mapping. Reusing the `<Agent>_ToolParams` JSON via `fda sa flow "<Agent>_flow.metadata.input" --jsonFile <file>` fixes the **runtime** schema (build/run correct) — but the designer treats `metadata.fe_metadata.input` (its cached view) as the **source of truth** and **regenerates `metadata.input` from it on save**. FDA never writes `fe_metadata`, so a flow whose `fe_metadata` is still empty gets your CLI schema **wiped back to a bare object the first time the user saves** (verified: two A2A flows were bare again after an open+save). Two ways to make it stick — do **one**: **(a)** the user clicks **"Sync"** once on each trigger (Sync writes *both* `metadata.input` and `fe_metadata` from the handler schema — the sanctioned, always-correct path); or **(b)** at build time also **bake `fe_metadata.input` (and `.output`)** to the exact shape a Synced flow has, so `metadata.input` survives regeneration and the fields render with no Sync (copy the format from an already-Synced flow — it's the designer's own output; see the bake template in [references/fda-build-recipes.md](references/fda-build-recipes.md) § gotcha 5). Because all three triggers (`tr_mcpserver`/`tr_agent`/`tr_wsserver`) are non-OpenAPI, keep **"click Sync on every trigger"** as the manual-config-gap fallback regardless (documented limitation "Manual Sync for Non-OpenAPI Triggers" — see [references/fda-limitations.md](references/fda-limitations.md)). The app builds and runs correctly either way — this is purely designer reconciliation.
9. **Never configure a `password` app property through FDA — it's a documented limitation; hand it to the user.** Per the official *Application Properties* limitation, FDA app properties support only **string / boolean / number**; the `password` type is **not supported** (the assistant silently converts it to `string`; the CLI `cap … password` errors `Unknown Flogo Property Type`). And `cap` writes the value as **plaintext** (FDA can't `SECRET:`-encrypt). The `#sendmail` `Password` field only accepts a **secret-valued** property, so a plaintext string one shows *"Type of field 'Password' (password) differs from bound app property (string)."* ⚠️ **Do NOT "fix" this by setting the property `type` to `password`** (in a prompt *or* by hand-editing the JSON) — that type is invalid and the designer **silently drops the property on the next save**, escalating the warning to a hard error: *"'Password' is bound to app property … which does not exist."* Correct handling: create the property as a `string` via FDA, then make it a manual-config-gap item — the user re-enters its value once in the designer's App Properties panel so it becomes `SECRET:…` (matches the working clone). Builds/runs as string either way; this only clears designer validation. (See [references/fda-limitations.md](references/fda-limitations.md).) 🔒 **This is a manual END-OF-BUILD handoff step — you cannot clear this ✗ from a file edit, and you must not try, even if the user explicitly asks you to make it a `password`-typed property (with a dummy value or otherwise).** The `SECRET:…` value is produced by the designer encrypting with the app's own key, so you cannot fabricate a valid one (a hand-written `SECRET:` blob fails at runtime), and forcing `"type":"password"` triggers the drop-on-save hard error above. When asked, explain this and point the user to App Properties (keep type `string`; entering *any* value there — even a dummy — encrypts it to `SECRET:` and clears the ✗); the working Hospital app confirms the end state (binding kept, `type:string`, `value:"SECRET:…"`). Always list "set `Email_App_Password` in App Properties" in the README manual-config gap section.
10. **PostgreSQL activity `input.Connection` must be the LITERAL `conn://<uuid>` — name-resolution silently writes an empty string.** Setting it via `fda sa activity "<flow>.<Act>.input.Connection" PostgresConn -C connection` produces `"Connection": ""`, which shows as an **empty connection dropdown** in the designer and fails at runtime with **"Connection is required"** (verified on every `act_postgresql_query`/`act_postgresql_insert` in a use case built this way). Fix: after `fda cc PostgresConn`, read the connection's UUID back from the `.flogo` (same pattern as gotcha 3's `conn://` arrays) and set the literal — `fda sa activity "<flow>.<Act>.input.Connection" "conn://<uuid>"`. The recipe's `conn_uuid()` helper does the readback; apply it to **every** query/insert activity in the MCP and A2A apps. (See [references/fda-build-recipes.md](references/fda-build-recipes.md) § MCP step 4.) ⚠️ **The ref must match the connection's CURRENT id, and that id is not stable across regeneration.** Re-running `fda cc` (e.g. re-running the whole build driver) or re-entering the DB credentials directly on the connection in the designer mints a **new** connection UUID; every activity ref still pointing at the old id becomes dangling and the designer silently clears it to `""` on the next save (verified: MCP survived because its refs still matched; A2A's were all empty after the connection id changed). **So once an app has been opened/edited in the designer, never "fix" it by regenerating the `.flogo`** — patch only the broken `Connection` field(s) on the existing file to the current id (or, in the designer, re-select the connection in each activity's dropdown). Re-running the driver also reverts every manually-entered secret back to its placeholder.
11. **Port app properties must match the trigger field's type: `tr_mcpserver`/`tr_agent` ports are `string`; `tr_wsserver` and the DB connection port are `number`.** The `tr_mcpserver` "HTTP Server Port" and `tr_agent` "A2A Server Port" fields are typed **string** — bind them to **`string`** app properties (`fda cap MCP_SERVER_PORT string …`, `fda cap <Agent>_PORT string …`) or the designer flags *"Type of field 'HTTP Server Port' (string) differs from the bound app property 'MCP_SERVER_PORT' (number)"* (verified). But the `tr_wsserver` "port" field and the PostgreSQL connection "Port" field are **numeric** — keep `WebSocket_PORT` and `PostgreSQL.PostgresConn.Port` as **`number`**. Don't over-correct: making the WS/DB port `string`, or the mcp/agent ports `number`, each reintroduces the mismatch. (See [references/fda-build-recipes.md](references/fda-build-recipes.md) § MCP step 1 / § Orchestrator step 1.)
