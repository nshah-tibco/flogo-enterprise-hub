# Verified gotchas (fda 0.9.5, Flogo 2.26.9, flogobuild 1.1.1)

Each of these broke a real build (the modules rebuilt in `examples/`). The scripts already handle them; keep them in
mind when you write logic scripts or debug.

## BW6 side

| # | Finding | Consequence |
|---|---|---|
| B1 | MCP tool names live in `META-INF/module.bwm` (`<operation tool="true">` + optional `<restMcpTool name scope>`), not in the `.bwp` | grep the `.bwm`; `analyze_bw6.py` does |
| B2 | With `-Dbw.enable.mcp.server=true`, a module **with** MCP-configured operations exposes only those; a module **without** any exposes every operation under its nickname (`post-api-approve`, ...) | Flogo default = explicit only; `--mcp all` for exact BW behaviour |
| B3 | BW tool description = operation `notes`; input schema = query/path params + body fields flattened; tool result text = the REST body JSON | `mcp_<tool>` flows reproduce exactly this |
| B4 | Reply mappings are stored in `<tibex:partBinding>`, activity inputs in `<tibex:inputBinding>` | analyzer reads both |
| B5 | BW "write" stub tools may return `approvalRequired:true` and write nothing | copy the stub; don't invent persistence |
| B6 | Unmatched `for-each` in a reply → Java 500; missing required param → HTML 400 | Flogo returns JSON 404/400 (IMPROVED) |
| B7 | Each `onMessage` branch parses **its own copy** of embedded data, and copies can differ (e.g. one product's return window is 45 days in one branch and 15 in another: `examples/orders_logic.py`) | take each flow's literals from its own branch (`L.bw_json(flow, '<activity>')`); report the inconsistency, don't silently pick one |
| B8 | BW's REST binding rejects unknown request fields with 400 | Flogo ignores them; record it in cases.json with `"accept": "<why>"` (verdict ACCEPTED) |
| B13 | A BW RAG ingest operation can ignore its own request (the parse step is dead), so a reset flag is ignored and every ingest appends duplicates to the vector DB (`examples/policy_logic.py`) | the Flogo app implements reset (delete + recreate the store); report it |
| B14 | BW RAG query infers each chunk's title/documentId from the chunk TEXT (`contains(text, "<a phrase of that document>")`) and its `retrieval[].text` carries appended metadata (score, createdAt ... concatenated to the text) | upload the metadata as file attributes and read it back from the search rows |
| B9 | BW processes can run activities whose output the reply never reads (e.g. a Java converter + ParseXml: `examples/inventory_logic.py`) | the analyzer marks them "nothing reads its result" and leaves them out of the difficulty rating — don't port them. Side-effect activities (JDBC update/SQLDirect, calls, sends) and anything a transition condition reads are never dead |
| B10 | BW can write to the DB and THEN fail ("missing reply" when an optional field is absent) | Flogo replies; record the case as ACCEPTED |
| B11 | A BW reply can contradict its own OpenAPI schema (e.g. integer counts rendered as strings: `examples/operations_logic.py`) | follow the schema; ACCEPTED |
| B12 | BW renders an XSLT `xsi:nil` element as JSON `null` (and nil lists as `[]`) | Flogo omits nulls (OMIT_NULLS) → EQUIVALENT; map empty lists explicitly as `[]` |
