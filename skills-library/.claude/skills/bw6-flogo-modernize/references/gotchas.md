# Verified gotchas (fda 0.9.5, Flogo 2.26.9, flogobuild 1.1.1)

Each of these broke a real build (the five REST modules of the `Retail_AI_BW_Flogo` sample). The scripts already handle them; keep them in
mind when you write logic scripts or debug.

## BW6 side

| # | Finding | Consequence |
|---|---|---|
| B1 | MCP tool names live in `META-INF/module.bwm` (`<operation tool="true">` + optional `<restMcpTool name scope>`), not in the `.bwp` | grep the `.bwm`; `analyze_bw6.py` does |
| B2 | With `-Dbw.enable.mcp.server=true`, a module **with** MCP-configured operations exposes only those; a module **without** any exposes every operation under its nickname (`post-api-approve`, ...) | Flogo default = explicit only; `--mcp all` for exact BW behaviour |
| B3 | BW tool description = operation `notes`; input schema = query/path params + body fields flattened; tool result text = the REST body JSON | `mcp_<tool>` flows reproduce exactly this |
| B4 | Reply mappings are stored in `<tibex:partBinding>`, activity inputs in `<tibex:inputBinding>` | analyzer reads both |
| B5 | BW "write" stub tools may return `approvalRequired:true` and write nothing | copy the stub; don't invent persistence |
| B6 | Unmatched `for-each` in a reply → Java 500; missing required param → HTML 400 | Flogo returns JSON 404/400 (IMPROVED) |
| B7 | Each `onMessage` branch parses **its own copy** of embedded data, and copies can differ (Orders: JKT-RAIN-210 window 45 days in one branch, 15 in another) | take each flow's literals from its own branch (`L.bw_json(flow, '<activity>')`); report the inconsistency, don't silently pick one |
| B8 | BW's REST binding rejects unknown request fields with 400 | Flogo ignores them; record it in cases.json with `"accept": "<why>"` (verdict ACCEPTED) |
| B13 | BW Policy ingest never reads its request (`ParseIngestRequest` is dead), so `resetCollection` is ignored and every ingest appends duplicates to Weaviate | the Flogo app implements reset (delete + recreate the store); report it |
| B14 | BW RAG query infers each chunk's title/documentId from the chunk TEXT (`contains(text, "Electronics including")`) and its `retrieval[].text` carries appended metadata (`0.82…createdAt2026-…`) | upload the metadata as file attributes and read it back from the search rows |
| B9 | BW processes can run activities whose output the reply never reads (Inventory: Java JsonToXmlConverter + ParseXml) | the analyzer marks them "nothing reads its result" and leaves them out of the difficulty rating — don't port them. Side-effect activities (JDBC update/SQLDirect, calls, sends) and anything a transition condition reads are never dead |
| B10 | BW can write to the DB and THEN fail ("missing reply" when an optional field is absent) | Flogo replies; record the case as ACCEPTED |
| B11 | A BW reply can contradict its own OpenAPI schema (Operations reset: integer counts rendered as strings) | follow the schema; ACCEPTED |
| B12 | BW renders an XSLT `xsi:nil` element as JSON `null` (and nil lists as `[]`) | Flogo omits nulls (OMIT_NULLS) → EQUIVALENT; map empty lists explicitly as `[]` |

## fda / Flogo side

| # | Symptom | Cause | Fix (in scripts) |
|---|---|---|---|
| F1 | Flow receives `queryParams = null` from `tr_rest` | `cas` writes `handler.schemas.output.queryParams.value` as the parameter **list**; runtime only parses a JSON-schema **object** (`trigger/rest/parameter.go`) — silent. `pathParams` are written correctly. Filed **FLOGO-20725** | `sa handler ...schemas.output.queryParams --jsonFile {value: <object schema>, fe_metadata: <list>} --force` (the scaffold also normalizes `pathParams`, harmless) |
| F2 | Missing param answered with plain-text 400 before the flow | `required` in that object schema makes the trigger validate | leave `required` out; validate in the flow (`require_params`) |
| F3 | `cas` GET flow has no `queryParams` input | `cas` omits query params from `flow.metadata.input` (tracked as **FLOGO-19157**) | `sms <flow>.input --json-schema ...` |
| F4 | `cm` FLOW_OUTPUT_VS_ACTION_OUTPUT_MISMATCH when one flow has REST + MCP handlers | cm requires every handler's `action.output` keys == flow outputs | thin `mcp_<tool>` flow per tool → `act_default_subflow` → actreturn |
| F5 | MCP tool returns empty text | `tr_mcpserver` uses `response.data` (string) as text, non-empty `response.error` → `isError` | `data = utility.renderJSON(body, false)`, `error = code >= 400 ? ... : ""` |
| F6 | Runtime: `failed to resolve activity attr: 'x', not found in activity 'Mapper'` | mapper outputs are under `.output` | `$activity[Mapper].output.x` (run `fda lms` first) |

| F13 | Python → fda crashes with `UnicodeDecodeError` / `UnicodeEncodeError` | box-drawing chars in `cm` output | `subprocess(..., encoding="utf-8")` and `python -I -X utf8` (`-I` ignores PYTHONIOENCODING) |
| F14 | Agent says "inventory system connection failed" after restarting an MCP server | orchestrator keeps the old MCP session | restart the orchestrator after any MCP server restart |
| F15 | `taskkill //PID` fails with "Invalid argument" | `MSYS_NO_PATHCONV=1` is exported, so `//` is not rewritten | use `/PID` when NO_PATHCONV is set, `//PID` otherwise |
| F16 | Designer: `Input` error on parsejson, red squiggles under the JSON | a literal starting with `{` in a **string** field is read as an object | seed a typed mapper array instead (`Logic.static_data`) |

| F18 | Designer shows an API key property as `string`, value in clear | `cap` writes plaintext | encrypt with `flogo-vscode-cli secret encrypt -p <v>` and `cap <name> string SECRET:...` (type stays string; the SECRET: value makes it a password) |
| F19 | No `abs()` in the Flogo mapper | — | top-level ternary `x < 0 ? coerce.toInt(0 - x) : coerce.toInt(x)` |
| F20 | Mapper schema misses nested keys that only some items have (e.g. `attributes.capacityLiters`) | schema inferred from the first item only | `infer_schema` deep-merges every item (fixed in the library) |
